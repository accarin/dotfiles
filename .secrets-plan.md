# Encrypted-secrets implementation plan (age + age-plugin-fido2-hmac)

STATUS: planning only, NOTHING implemented yet. This file is a working/tracking
doc, deliberately named with a leading `.` (not `.chezmoi*`) so chezmoi's
source-state walker ignores it entirely -- it will never be deployed as a
dotfile target. Delete this file once the implementation is done and verified
(its durable summary should move into `/memories/repo/chezmoi-notes.md`
instead).

## Problem statement

`.chezmoidata.toml` (public repo!) currently stores plaintext per-machine
`dot.client_id` values (AdGuard DNS-over-TLS ClientIDs -- low-stakes but
API-key-like bearer tokens). Need these encrypted at rest, reliably usable
across multiple machines, ideally leveraging the existing FIDO2/U2F hardware
keys (`u2f_keys.accarin` pool in `.chezmoidata.toml`) for "something you have"
protection -- while still working on machines that have no physical key
available (headless Hetzner VPSes: nxs-1, atm-1, and future ones).

## Chosen approach: age encryption, two identity classes

1. **Primary (desktop/gaming/notebook, physical key always available):**
   `age-plugin-fido2-hmac`, **Group 1** mode (no separate per-key identity
   file -- uses a single, universal, fixed "dummy" identity string from
   `age-plugin-fido2-hmac -m`, identical for every user of this mode, safe to
   commit to a public repo). Decryption requires physically touching one of
   the enrolled FIDO2 keys (+ optional PIN); the plugin's security goal SG-1
   guarantees the salt+credential-ID metadata alone is NOT sufficient to
   decrypt without the physical device.
2. **Fallback (headless servers, no physical key):** a plain `age-keygen`
   X25519 identity (no FIDO2/plugin involvement at all -- just stock `age`,
   already packaged in Debian trixie as 1.2.1). Its private key IS a real
   secret and is distributed manually via `scp` over the existing
   already-authenticated SSH channel, stored locally at
   `~/.config/chezmoi/age-fallback-identity.txt` on that server only, never
   committed to git.

## Why per-machine encrypted files (not one shared file)

`.chezmoidata.<format>` itself cannot be encrypted or templated (read before
the template engine starts) -- confirmed via chezmoi docs. So secrets live in
separate small age-encrypted files, read via
`{{ include | decrypt | fromToml }}`.

Originally planned as ONE shared `.chezmoi-secrets/secrets.toml.age` file with
`[machines.<hostname>.<domain>]` sections (mirroring `.chezmoidata.toml`'s
convention). CORRECTED after considering the server fallback: a single shared
file encrypted to (7 FIDO2 recipients + N server fallback recipients) means
ANY server's leaked fallback private key can decrypt EVERY machine's secrets,
not just its own -- unacceptable blast radius for a fleet of Hetzner VPSes.

FIX: **one encrypted file per machine**, each independently encrypted to a
per-file recipient list:
- Desktop/gaming/notebook machines: recipients = the 7 FIDO2 public keys only.
- Server machines: recipients = the 7 FIDO2 public keys **+** that specific
  server's own fallback public key.

This means:
- You (holding a physical FIDO2 key) can always decrypt/re-encrypt ANY
  machine's secrets file from your own workstation -- you're always a
  recipient everywhere.
- Each server can decrypt ONLY its own file via its local fallback identity.
- A single compromised server never exposes any other machine's secrets.

## File layout (planned)

```
.chezmoi-secrets/
  age-identity.txt          # committed: universal Group-1 dummy identity
                             # (output of `age-plugin-fido2-hmac -m`, safe to
                             # publish, identical for every host using it)
  secrets/
    deep-thought.toml.age    # per-machine encrypted secrets
    silverhand.toml.age
    pc46379.toml.age
    hitchhiker.toml.age
    nxs-1.toml.age           # (if/when nxs-1 gets its own secrets, e.g. dot.client_id)
    atm-1.toml.age
    ...
.chezmoitemplates/
  decrypt-secrets            # reusable partial: given .chezmoi.hostname,
                              # stat-guards for existence (missing file ->
                              # empty dict, NOT an error -- reuses the
                              # existing `stat` truthy/falsy pattern already
                              # used elsewhere in this repo), then
                              # include | decrypt | fromToml the per-host file
```

Each per-machine `.toml.age` file's PLAINTEXT contents are flat (no
`[machines.<hostname>...]` nesting needed since the file is already scoped to
one host), e.g. for `deep-thought.toml.age`:
```toml
[dot]
client_id = "9rq4yk6n7pk79o6vj3vjwo67"
```

## Config changes

- `.chezmoi.toml.tmpl`: add `encryption = "age"` + `[age]` block. BRANCHED by
  `machine_type`:
  - non-server: `identity = "<sourceDir>/.chezmoi-secrets/age-identity.txt"`,
    `recipients` = the 7 FIDO2 public keys (hardcoded list, filled in after
    enrollment).
  - server: `identity = "~/.config/chezmoi/age-fallback-identity.txt"` (local,
    scp'd, never committed).
- `.chezmoidata.toml`: remove the 4 plaintext `client_id = "..."` lines
  (everything else in the `[dot]`/`[machines.*.dot]` blocks stays -- `enabled`,
  `interface_match` etc. are not sensitive).
- `run_onchange_install-packages.sh.tmpl`: add `age` to `PACMAN_PKGS` (desktop)
  and to `DEBIAN_PKGS` (server/wsl, confirmed packaged in trixie); add
  `age-plugin-fido2-hmac` to `AUR_PKGS` (desktop only -- NOT needed on
  servers, they use plain age-keygen identities, no plugin/libfido2 dependency
  there at all).
- `run_onchange_setup-dot.sh.tmpl`: replace the plaintext
  `.machines.<host>.dot.client_id` lookup with
  `{{ template "decrypt-secrets" . }}` + a `hasKey`-guarded lookup into the
  decrypted dict; keep the existing warn/suggest-clientId/`exit 1` UX for a
  genuinely missing entry.

## Manual steps (physical hardware / secrets -- cannot be automated by the agent)

1. For **each of the 7 keys** (T2 Maxi M1/M2, T2 Mini U1/U2/C1, Legacy
   Mobile, Legacy Home): `age-plugin-fido2-hmac -g`, choose **Group 1**,
   decide per-key whether to require a PIN, record the printed recipient
   (`age1...`).
2. Once, with any one key: `age-plugin-fido2-hmac -m` -> save output as
   `.chezmoi-secrets/age-identity.txt` (committed).
3. Per machine, build the plaintext `<hostname>.toml` staging file, encrypt
   with `age -r <recip1> -r ... [-r <server-fallback-recipient-if-any>] -o
   .chezmoi-secrets/secrets/<hostname>.toml.age <hostname>.toml`, then delete
   the plaintext staging file. (NOT using `chezmoi encrypt`/configured
   `age.recipients` for this, since recipients differ per file -- that config
   knob is only for the common case of ad-hoc `chezmoi add --encrypt` of some
   other future dotfile.)
4. For each headless server: `age-keygen -o age-fallback-identity.txt` on
   your workstation, `scp` the private-key file to
   `~/.config/chezmoi/age-fallback-identity.txt` on that server (mode 600),
   and include its printed public key as an extra recipient when encrypting
   that server's own `<hostname>.toml.age` (step 3).

## Open items / to verify during implementation

- Confirm `age-plugin-fido2-hmac -m` really prints a fixed, credential-
  independent dummy identity (inferred from README wording, not yet
  hands-on-verified).
- Confirm `age` apt package name/version behaves as expected on the actual
  Debian trixie servers (madison shows 1.2.1-1 available, not yet installed
  there).
- UX note accepted as a trade-off: every separate `decrypt` call in a
  `chezmoi apply` run is a fresh hardware touch challenge (no caching across
  calls) -- fine for now (single `dot.client_id` consumer), revisit if many
  more secrets/scripts start needing decryption in the same apply run.
- Scope is intentionally general-purpose (not just `dot.client_id`) per
  explicit user decision -- new secrets just get new keys added to the
  relevant per-host TOML before re-encrypting.

## Decisions already confirmed by user (2026-07-22)

- Group 1 (simple, no per-key identity files) over Group 2 (unlinkable).
- Enroll all 7 existing physical FIDO2 keys, not just a subset.
- Commit the (provably public-safe, per spec SG-1) identity material to the
  repo rather than keeping it local-only.
- Build the mechanism generally, not scoped narrowly to just `dot.client_id`.
- Fallback distribution via manual `scp` is explicitly acceptable.
